PostgreSQL Schema & Table Relationships

The data model behind the invoicing tool — five tables covering login, customers, invoices, line items and staged payments. Built for Django, frozen on issue, money kept in exact decimals.

Entity relationships

How the tables connect

Everything hangs off invoice. A customer places many invoices; each staff login creates many; every invoice owns its line items and collects payments in stages. Crow's-foot marks the "many" end.

Computed, not stored

Values the queries derive

These never become columns — storing them would let the document drift from the ledger. They're computed from the frozen rows above whenever needed.

# per invoice
amount_paid = Σ payment.amount (all rows for the invoice)
advance_paid = Σ payment.amount where kind = ADVANCE
balance_due = invoice.grand_total − amount_paid

# dashboard
monthly_income = Σ payment.amount where paid_at within the month
bucket counts = count(invoice) grouped by status

# PDF engine flags — all derived at render time
show_paid_stamp = (status == PAID)
paid_date = max(payment.paid_at) where kind = BALANCE
show_warranty_stamp = (warranty_stamp != NONE)
show_term_4 = any(line_item.has_warranty == true)
Rules that keep it correct

Modeling decisions

01 Exact decimals, never float

Every money and quantity field is NUMERIC / Django DecimalField. Float rounding on a financial document is a bug, not a rounding quirk. Quantity is (12,4), money is (12,2).

02 Freeze on issue

Once issued, invoice and its line_item rows are read-only. Totals are saved, not recomputed. A correction is a new invoice or a cancellation — never an edit. This is what makes regenerate-on-download safe.

03 Payments are rows, not fields

Recording an advance or clearing the balance appends a payment row and flips status. The invoice body is never mutated, and each event keeps its own timestamp.

04 Server owns the numbers

Invoice number, line totals, grand total and balance are all computed in Django. The front end — or the PDF engine — only renders finished values it is handed.

05 Gap-free numbering

Generate invoice_number inside a transaction (a PostgreSQL sequence, or a small invoice_counter(year, last_no) table) so two concurrent issues can't collide or skip a number.

06 Timezone-aware times

All timestamps are TIMESTAMPTZ, stored in UTC and shown in Asia/Colombo. Payment timestamps must be exact to satisfy the "date & time paid" requirement.
